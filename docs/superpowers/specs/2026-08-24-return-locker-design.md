# 智能更衣柜 v15 离场还柜设计

日期：2026-08-24  
状态：用户已确认，可实施  
基线：v14（必须保留原源码副本及 APK，不覆盖）  
目标终端：RK3288、Android 7.1.2、1280×800

## 1. 目标

在现有“用柜/取柜”功能外新增独立的“离场还柜”业务。用户完成身份认证后，只能看到服务器确认属于自己的在用柜门；用户确认开柜、取走物品并关门后，终端必须检测到一次真实的“关→开→稳定关”状态变化，才向服务器提交还柜完成并释放柜门。

v15 暂无正式业务接口，因此仅在 `localDemo` 构建使用明确标识的内置模拟服务形成可交互闭环；`production` 构建必须失败关闭，不能用本地白名单代替服务器授权。

## 2. 不可突破的边界

- v14 及历史 APK、历史串口功能、12 个既有柜门指令保持不变。
- 不根据柜号在还柜流程中临时计算或猜测开锁指令；模拟服务返回固定的、完整的授权指令，正式版未来逐次使用服务器下发指令。
- 每次还柜开门前必须有一次本次会话、本柜门、未过期的服务器授权，并由用户点击确认。
- 断网或服务器不可用时禁止还柜开锁，显示网络异常弹窗。
- 一次只处理一个柜门、一个串口开锁动作和一个关门监听，多个柜门按队列逐个完成。
- 开锁 ACK 只表示锁控板接受了开锁命令，不等于用户已经关门或服务器已经完成还柜。
- 柜门关闭超时不能自动释放柜门；状态保留为“待关门”，允许继续检测、重新开门或由管理员处理。
- ID/二维码扫描器与进程级串口继续长期占用；摄像头和掌纹设备仅在用户选择对应认证方式后启动，退出页面立即释放。

## 3. 用户流程

### 3.1 入口与认证

1. 首页点击“离场还柜”。
2. 进入专用还柜认证页，不复用普通“任意选柜”权限。
3. 可使用手机号/密码、持续监听的 ID 卡/二维码、人脸或掌纹认证。
4. 人脸和掌纹先进入二选一页；选人脸后才检查网络、百度授权、模型和摄像头，选掌纹后才检查掌纹设备。
5. 认证凭证提交模拟/正式服务器查询当前用户的在用柜门。

### 3.2 柜门列表与操作

- 没有在用柜门：提示“未查询到需要归还的柜门”，8 秒后回首页。
- 一个柜门：展示服务器柜号、区域和确认按钮。
- 多个柜门：只展示服务器返回的柜门列表；用户逐个处理，不出现未授权柜门。
- 用户确认后终端检查网络、授权时效、串口连接，再发送服务器给出的精确指令。
- 开锁成功后页面进入“请取出物品并关闭柜门”，开始门状态确认。

### 3.3 关门确认

锁控板单锁状态查询格式：`80 <板地址> <锁地址> 33 <异或校验>`；响应：`80 <板地址> <锁地址> <00|11> <异或校验>`。

默认反馈极性 `SHORT_WHEN_LOCKED`：`11=已关`、`00=已开`。板卡若配置为相反极性，由设备配置显式切换，不能自动猜测。

判定规则：

1. 开锁前或开锁后立即建立基线，确认初始状态为“关”。
2. 必须观察到至少一次“开”。若从未观察到开门，即使连续返回“关”也不能完成还柜。
3. 观察到“开”后，连续两次有效查询均为“关”才判定稳定关门。
4. 查询帧要求板地址、锁地址和 XOR 全部匹配当前操作；旧操作和其他柜门响应全部忽略。
5. 支持的板卡若主动推送 `82 ...`，只把它当作立即复查的触发信号，最终状态仍以主动查询为准；开锁指令窗口内的 `82` 不直接完成流程。
6. 查询超时、串口断开或状态不确定时继续保持“待关门”，不向服务器提交完成。

建议查询节奏：正常每 500 ms 查询一次；检测到开门后可维持 500 ms；连续通信失败时退避到 1 s，并在恢复后继续原操作。每次响应只影响当前唯一的关门监控器。

### 3.4 完成与多柜门

稳定关门后向服务端提交 `operationId + lockerId + completionToken`。模拟服务返回成功后把该柜门标记已归还；若还有柜门，进入下一柜门确认；全部完成后展示成功页并在 8 秒后回首页。

提交失败时保留本地“已观察到稳定关门”的会话快照，只允许幂等重试同一个 `operationId`，不能再次释放柜门或改换命令。

## 4. 组件设计

### 4.1 还柜领域模型

新增独立 `returnflow` 包，避免普通用柜 `KioskFlowModel` 获得错误权限：

- `ReturnIdentity`：一次认证所得的方法和不可变凭证快照。
- `ReturnLocker`：服务端柜门 ID、显示编号、区域、`LockerTarget`。
- `ReturnAuthorization`：操作 ID、目标柜门、完整开锁命令、预期成功/失败帧、完成令牌、过期时间。
- `ReturnServiceClient`：查询在用柜门、取得逐次开门授权、提交归还完成。
- `ReturnFlowModel`：`HOME/AUTHENTICATING/LOADING/SELECTING/CONFIRMING/OPENING/WAITING_FOR_CLOSE/COMMITTING/SUCCESS/FAILURE` 状态机。

所有 byte 数组在构造和读取时防御复制；状态跳转校验操作代次，旧回调不能改变新页面。

### 4.2 服务实现

- `localDemo`：固定模拟用户与固定柜门/命令映射，明确显示“本机模拟数据”。ID 卡可映射 A1，二维码可映射 A1+A2，用于覆盖单柜和多柜流程。
- `production`：在正式接口未提供前只返回“服务尚未接入”，永远不签发开锁授权。
- 后续正式客户端替换 source-set 组装类即可，不改 UI、状态机、串口或关门监控。

### 4.3 串口授权边界

现有普通开柜路径继续调用旧接口。还柜新增 `AuthorizedUnlockRequest`，由 `UnlockCoordinator` 发送授权对象中的精确命令，并只接受该对象携带的预期响应。

`CustomerSerialWritePolicy` 增加窄化阶段：

- `RETURN_UNLOCK`：同一操作只允许一次授权对象中的精确开锁 payload。
- `DOOR_STATUS`：只允许当前目标的精确单锁状态查询帧。

禁止“任意 8A”或“任意 80”通配。操作结束、超时或页面退出后立即注销白名单。

### 4.4 UI

- 首页增加醒目的“离场还柜”按钮，其他布局和 1280×800 风格保持一致。
- 还柜认证页说明当前是还柜流程，并保留手机号/密码、ID/二维码自动监听、人脸/掌纹入口。
- 还柜柜门页只显示服务端返回的本人柜门，不允许翻到普通柜门布局。
- 处理中页面清晰显示：正在开柜、请取物并关门、正在确认关门、正在提交、完成/异常。
- 所有失败页面提供“重试”和“返回首页”；无操作 8 秒自动回首页的页面显示倒计时。

## 5. 稳定性与生命周期

- 每个异步流程携带 `generation + operationId + lockerId`；不匹配则丢弃。
- 串口仍由进程级 `SerialGateway` 持有，离开页面不关闭。
- 页面进入后台时停止客户 UI 定时器，但不把柜门误判为已还；恢复后重新查询当前状态。
- 摄像头/掌纹设备在离开对应识别页、超时、成功或 Activity 停止时立即释放。
- 模拟服务不睡眠阻塞 UI；回调统一回主线程并再次核对代次。
- 运行日志只记录操作 ID、柜门、状态、HEX 和耗时，不记录密码、人脸照片、二维码完整内容或服务 token。

## 6. 测试与验收

### 6.1 纯 JVM

- ReturnFlowModel 的合法/非法状态跳转、过期授权、旧回调、多柜顺序、提交重试。
- localDemo 单柜、多柜、未知凭证、幂等完成；production 永不下发授权。
- 门状态帧的生成、XOR、碎片/粘包、错误地址、极性反转。
- `关→开→关→关` 才完成；`关→关`、`开→关→超时`、串口断线均不完成。
- 精确授权命令和状态查询白名单；普通开柜指令回归不变。
- 首页/还柜页源代码契约和 8 秒恢复逻辑。

### 6.2 构建与现场

- common 与 localDemo 全量 JVM 测试通过；localDemo/production Android 编译、D8、资源、签名通过。
- v14 APK 的大小和 SHA-256 构建前后不变，v15 输出独立 APK。
- 桌面环境不声称完成真机 RS485 验收。RK3288 现场至少验证：持续串口连接、A/B 板柜门、开门后关门检测、门未关超时、断网禁止、单柜/多柜、ID/二维码、人脸入口与 50 次重复操作。
