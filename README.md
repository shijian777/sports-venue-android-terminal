# 智能更衣柜 v21 前端集成测试版

> **GitHub 私有源码快照（2026-09-12）**：保留当前工作目录的业务源码、测试、界面资源和 SDK 依赖；不包含真实签名密钥、APK、设备日志、构建缓存及旧 Git 历史。首次构建前请阅读 [源码恢复与配置说明](GITHUB-SOURCE-NOTES.md)。本仓库不是无需配置即可联网开柜的发行包。下文保留原工程说明，其中部分历史接入状态可能早于当前代码，不应作为整机验收结论。

这是面向 `1280×800` 横屏安卓柜控终端的 v21 前端集成测试版，继续在原 v17 工程中构建。57 个页面与对应交互已接入本地界面层，不代表所有线上功能已完成。保留 v18 的设备注册、JSON 响应兼容和场馆同步修复，v19 的身份响应修复，以及 v20 的第一步前端修复。本次集成适配最新基础设置状态字段与严格的数字/字符串页码响应，同时保留既有柜号、区域名、顺序、物理通道、原样开锁命令和授权边界。保留原有 `localDemo` 与 `production` 分离，不代表现场整机已经验收。下文既有功能与历史接入说明保留，实际开放边界仍以当前运行配置和验收结果为准。

## 当前功能

- 普通存/取柜：保留首页手机号、取柜码及原有选柜流程。柜区名称、柜号、排序和开锁命令由业务数据提供；选柜页按每页最多 `4×8=32` 个柜门展示，并支持分区和分页。
- ID 卡/手环与二维码：扫码器和读卡器在应用运行期间持续监听，不需要先点击入口。完整凭证作为不透明字符串处理，不把位数写死；识别后交给当前构建的认证服务校验。
- 人脸识别：按需启动。只有用户进入人脸流程后才申请摄像头、执行百度 SDK 检测/抓拍，并把结果交给认证服务；首页不会持续占用摄像头。
- 掌纹识别：掌纹设备尚未接入。`localDemo` 只提供明确标注的模拟通过；`production` 不提供模拟或本地放行，当前直接提示不可用。
- 离场还柜：身份校验后只展示服务端授权的在用柜，不允许用户任意选择其他柜门；有多个在用柜时逐个归还。

## 离场还柜流程

1. 用户点击首页“离场还柜”，使用手机号/密码、持续监听的 ID/二维码、人脸或掌纹完成身份认证。
2. `localDemo` 使用固定模拟数据返回待归还柜和对应串口帧；正式 `production` 必须由服务器返回授权柜门和本次精确命令。在正式接口未接通时一律失败关闭，绝不回退到本地白名单、模拟命令或任意开柜。
3. 页面展示服务器授权的待归还柜，用户必须明确确认后才能开门。
4. 每次操作先用精确的单门状态查询建立 `CLOSED` 基线，再只发送一次服务器授权的精确开锁帧。写入未被串口层接受时不会进入下一状态，也不会自动换算或替换命令。
5. 开锁应答只表示开锁请求被接受，不表示还柜完成。系统随后轮询同一板、同一锁，必须依次观察到 `OPEN → 连续两次 CLOSED`。
6. 用户点击“柜门已关闭”只会触发一次新的硬件状态查询；按钮本身不能直接提交。只有这次新查询仍返回 `CLOSED`，才向业务服务提交归还结果并生成完成回执。
7. 超时、串口掉线或状态不确定时保留当前流程并继续安全查询，不重复发送开锁命令。`82` 主动上报只用于提示立即查询，不能直接作为门已开或已关的依据。

单门状态协议使用：

```text
查询：80 <板地址> <锁地址> 33 <XOR>
返回：80 <板地址> <锁地址> <00或11> <XOR>
```

当前按“上锁短路型”解释状态：`11=CLOSED`、`00=OPEN`。只接受同板、同锁且 XOR 正确的完整响应。

## 认证与构建边界

- `localDemo`：用于无服务器条件下跑通普通流程和离场还柜模拟；掌纹也是模拟能力。
- `production`：所有身份、柜门列表、精确开锁指令和完成提交均应由正式服务器接口决定；缺接口、断网、超时或响应不合法时失败关闭，不允许使用本地模拟兜底。

## 当前服务器接入边界

本版本已经实现终端序列号读取、固定 HTTPS 传输以及 `checkDevice`、`baseSetting`、`basicData` 三条启动只读接口的请求、严格解析、重试、取消和页面状态链路。`production` 测试包会读取 RK3288 终端序列号并连接固定测试域名：先调用 `checkDevice` 完成设备备案检查，再使用返回的商户号和设备号请求 `baseSetting`、`basicData`。任何一步断网、超时、签名失败、设备未备案或响应不合法都会失败关闭并显示对应状态。

当前接入范围只开放这三条启动只读接口。三条接口全部成功后进入 `READY_READ_ONLY`，仍不会启用顾客认证、串口开柜、离场还柜、人脸比对或掌纹等实体效果；这些动作必须等各自正式接口和真机合同确认后再逐项放开。因此，本次联网不会向锁板发送开锁指令，也不会因服务器启动数据成功而自动执行柜门操作。

测试签名凭据只通过固定 production 组装路径提供：工厂调用副本和每次请求副本使用后立即清零，服务持有的运行期主副本在 runtime 关闭时清零；不从环境变量、系统属性、构建参数或本地文件读取，不写日志、不展示到页面，APK 审计同时拦截测试明文进入全部 DEX 命名空间。接收依赖的 package-private constructor 仍只允许 server 包测试使用 fake 数据，真实运行只能通过固定 HTTPS host、系统时钟和严格 transport 的 `createLive` 工厂构造。

这仍是测试域名、测试凭据和调试签名构建，不是长期生产密钥方案。上线前应由后端轮换测试阶段使用过的参数，并改成可过期、可吊销、按终端隔离的凭据；APK 和运行进程中的凭据都可能被有权限的人员恢复，不能把当前测试参数直接当作正式长期通用密钥。

API 25 lint、JVM 测试、DEX/Manifest 审计只能证明代码和包边界，不替代 RK3288 真机的序列号、TLS、系统时间、生命周期、锁板和柜门传感器验收。当前构建使用 `versionName 21.0-frontend-integration-test`；较早规格和内部构建目录中的 v17 名称不代表正式发布版。
- 人脸摄像头按需占用；串口、ID 读卡器和二维码扫码器按其职责长期监听或持有，避免页面切换导致反复重连。
- 本工程生成的是调试/联调用签名 APK，不是生产发布签名包。
- APK 保留 `armeabi-v7a + arm64-v8a 两 ABI`，其中 RK3288 使用 `armeabi-v7a` 原生库；构建执行 `CAMERA、INTERNET、ACCESS_NETWORK_STATE 三项权限精确检查`。
- 纯 JVM 测试和本地 Android 构建不能代替 RK3288、`1280×800` 屏幕、摄像头、扫码器、读卡器、RS-485 锁控板及柜门传感器的实体机验收。

## 管理员串口

首页管理员入口进入串口调试页面。串口由应用进程级所有者长期持有：离开管理员页、进入顾客页或切换认证页面不会自动关闭。只有管理员手动关闭串口，或应用进程被系统清理/退出时才释放。

顾客流程通过统一串口网关发送，避免管理员调试与业务开锁并发写入。管理员页仍可查看原始 HEX 收发和诊断信息；顾客页面不展示串口路径、板地址、校验字节等技术细节。

## 已知 SDK 组件边界

百度 FaceSDK 所需的 `com.baidu.liantian.LiantianActivity` 依现有 vendor 合同保持 `exported=true` 且未声明组件权限，因此其他本机应用可以显式启动该 SDK Activity。production 审计会锁定该组件的精确 action、category、theme 和 launchMode，任何扩张都会失败；本测试版不把这个已知攻击面描述为已消除。

## 本地构建

在 v17 工程根目录运行：

```powershell
.\scripts\build-debug.ps1 -Variant localDemo
.\scripts\build-debug.ps1 -Variant production
.\scripts\build-debug.ps1 -Variant all
.\scripts\audit-production-apk.ps1 -Apk ..\..\outputs\智能更衣柜-v21-production测试版.apk
.\scripts\verify-bootstrap-integration.ps1
```

第一步前端修复交付 APK：

```text
..\..\outputs\智能更衣柜-v21-localDemo.apk
..\..\outputs\智能更衣柜-v21-production测试版.apk
```

只有 `localDemo` 构建会保留本地模拟能力。`production` 和 `all` 每次都会在复制前自动运行机器安全审计；production 审计失败时不会复制或覆盖交付 APK。审计包含签名、包/版本、Manifest/权限、app-only DEX、源码安全规则、双 ABI 原生库和七个固定模型。这两个 APK 均使用调试/联调签名，不是生产发布签名包。
